# GitHub 오픈소스 수정 워크플로

사용자가 정한 GitHub 작업 규칙을 그대로 따른다. 코드 수정보다 이슈가 먼저이고, PR은 반드시 브랜치에서 열며, 고치면 이슈를 바로 닫는다. 이슈·댓글·PR 글은 실제 사람이 쓴 것처럼 짧고 반말로 쓴다.

## 작업 분류

| 들어온 요청 | 처리 경로 |
| --- | --- |
| "이건 아니야", "이게 불편해", 버그 제보 | 이슈 먼저 → 진행 댓글 → `fix/issue-<번호>` → PR → 이슈 닫기 |
| "스스로 버그 찾아 고쳐"로 네가 찾은 버그 | 위와 똑같이. 제보자 없어도 이슈를 먼저 연다 |
| "이 기능 추가해줘"처럼 요구가 완성된 경우 | 이슈 없이 `feat/<짧은-요약>` 브랜치 → PR |

분류가 애매하면 이슈를 여는 쪽을 택한다. 버그인데 이슈 없이 커밋부터 하는 것이 이 규칙에서 가장 큰 실수다.

## 자동 발동 조건

오픈소스 프로그램을 수정하는 중이거나 바이브 코딩 중에 사용자가 문제를 제보하면 이 스킬을 바로 불러낸다. "이거 문제야", "이거 안 돼", "오류 나", "안 되던데", "불편해", "버그 같아" 같은 말이 모두 신호다. 슬래시 명령을 기다리지 말고 위 작업 분류에 따라 이슈부터 연다. 문제 제보가 아니라 요구가 완성된 기능 추가만 별도로 `feat/` 브랜치로 간다.

## 함께 설치되는 스킬

`humanize-korean`은 이 저장소에 `skills/humanize-korean/`으로 같이 들어있다. 설치 스크립트가 `github-oss-workflow`와 `humanize-korean`을 항상 한 번에 넣으므로 따로 설치할 필요가 없다. 둘 중 하나만 설치된 상태는 이 스킬의 버그다. 에디터에서 안 보이면 `install.ps1`이나 `install.sh`를 다시 돌려 두 개를 같이 설치한다.

## 필요한 자료 읽기

1. 모든 작업에서 [references/workflow.md](references/workflow.md)를 먼저 읽는다. 사용자 규칙의 원문이다.
2. 이슈 본문·댓글·커밋 메시지·PR 본문을 쓸 때 [references/human-tone.md](references/human-tone.md)를 읽는다.
3. `humanize-korean`이 같이 설치돼 있으므로, 문장이 AI처럼 읽히면 `$humanize-korean`으로 다듬는다. 이때도 `~음·~함` 반말 register를 유지하고 격식체로 바꾸지 않는다. 근거 없는 경험·수치·출처를 새로 만들지 않는다.

## 버그 처리 순서

1. **이슈를 먼저 연다.** `gh issue create`로 한국어 본문을 쓴다. 증상, 재현 절차, 원인(아직 모르면 확인 중이라고 적고 나중에 댓글로 보완), 기대하는 동작, 환경을 문단으로 담는다. 템플릿칸을 채우지 말고 문장으로 쓴다.
2. **원인을 파고드는 동안 이슈 댓글을 남긴다.** `gh issue comment <번호> --body "..."`. 확인된 것과 아직 없는 것을 구분해서 적는다.
3. **브랜치를 만든다.** `git switch -c fix/issue-<번호>`. main에 직접 커밋하지 않는다.
4. **커밋한다.** 커밋 메시지도 한국어 사람 톤으로 짧게 쓴다.
5. **PR을 연다.** `gh pr create` 본문에 `Closes #<번호>`를 넣어 이슈와 연결한다.
6. **이슈를 바로 닫는다.** `gh issue close <번호> --comment "..."`. 원인 확인 → 수정 완료 → PR 링크 흐름을 댓글로 남기고 한 줄로 마무리한다. PR만 열어두고 이슈를 열어두는 상태로 끝내지 않는다.

## 기능 추가 순서

이슈를 열지 않는다. `git switch -c feat/<짧은-요약>`에서 커밋하고 `gh pr create`로 PR을 연다. PR 본문도 사람 톤 한국어로 쓴다.

## 글쓰기 핵심

- 3~5문단 이내. 서론·결론·요약으로 감싸지 말고 바로 내용.
- 번호 매긴 목록, `---` 구분선, `**강조**`, 표 같은 정돈된 포맷 남발 금지. 필요하면 짧게 `- `로 나열.
- 존댓말 금지. `~습니다`, `~이네요`, `~해 주세요`, `고쳐보겠습니다` 다 쓰지 않는다. 반말 + `~음`, `~함`, `~더라`, `~거든`으로 끝낸다.
- "분석결과", "원인을 파악했습니다", "기대하는 동작", "다시 한번 확인해 주세요", "도와드리겠습니다", "감사합니다" 같은 상투 표현 금지.
- 한 문단에 사실 2~3개씩 흘려보낸다. 이모지는 사용자가 썼을 때만.
- 저장소 주 언어를 따른다. 한국어 저장소면 전부 한국어로 쓴다.

## 절대 지키기

- 이슈를 열기 전에 코드 수정 금지.
- 이슈 댓글 없이 커밋만 하거나 PR만 열어 끝내지 않는다.
- 고치기가 끝나면 이슈를 즉시 닫는다.
- 과거 이력이 main 직접 커밋이어도 지금은 브랜치 + PR을 기본으로 한다.
- 사용자가 명시적으로 다른 방식을 지정하면 그 요청이 이 규칙보다 우선한다.

## 완료 전 체크

- 이슈 번호를 확인했는가
- 원인 확인/수정 완료/PR 링크 댓글을 남겼는가
- 브랜치 이름이 규칙에 맞는가
- PR 본문에 `Closes #<번호>`가 있는가
- 이슈가 닫혔는가

## 결과 반환

이슈 번호, 브랜치 이름, PR URL, 이슈 종료 상태를 짧게 알려준다. 긴 설명이나 정돈된 표는 붙이지 않는다.

## 도구

`gh issue create`, `gh issue comment`, `gh issue close`, `gh pr create`, `gh pr comment`, `git switch`, `git commit`.
